Prompt

Use the documentation in project-setup/index.mdx as the authoritative source of truth for building the project.

Primary Objective

Your task is to fully implement the project described in the documentation, not merely analyze, summarize, plan, or explain it.

You must:

Read and follow project-setup/index.mdx completely.

Recursively follow all links, references, navigation entries, imports, setup guides, prerequisite documents, and related documentation referenced from index.mdx.

Continue processing documentation until no additional setup-related documentation remains that could affect implementation.

Build the actual project exactly as specified by the documentation.

Documentation Processing Rules

  • Treat the documentation as a complete specification.
  • Apply instructions in the order intended by the documentation.
  • If a document references another required document, process that document before continuing.
  • If documentation files conflict:
  • Prioritize the most specific instruction.
  • Prioritize newer documentation over older documentation when versioning information is available.
  • Record all conflicts and resolutions in the implementation log.
  • Do not invent requirements, features, dependencies, APIs, files, architecture, workflows, or behavior that are not specified by the documentation unless absolutely necessary to resolve ambiguity.
  • Any implementation decision made to resolve ambiguity must be documented in the implementation log.

Implementation Requirements

Create all required:

  • Directories
  • Source files
  • Configuration files
  • Environment files
  • Scripts
  • Dependencies
  • Infrastructure definitions
  • Build configurations
  • Documentation artifacts
  • Tests (if specified)

Do not leave placeholders, TODOs, mock implementations, stubs, incomplete integrations, or partially completed features unless the documentation explicitly requires them.

Avoid duplicating files, dependencies, configurations, or setup steps that already exist unless the documentation explicitly requires modification.

Required Implementation Log

Create a root-level file named:

SETUP_STEPS.md

Update this file continuously throughout the implementation process rather than generating it only at the end.

The log must include:

Documentation Processed

  • Each documentation file reviewed
  • The order in which files were processed

Files and Directories

  • Files created
  • Files modified
  • Directories created

Commands Executed

  • Installation commands
  • Build commands
  • Test commands
  • Validation commands

Dependencies

  • Packages installed
  • Versions selected
  • Reasons for any version deviations from documentation

Configuration Changes

  • Environment variables added
  • Configuration files created or modified
  • Infrastructure changes

Decisions and Assumptions

  • Ambiguous instructions encountered
  • Assumptions made
  • Alternative approaches considered
  • Conflict resolutions

Validation Results

  • Build results
  • Test results
  • Lint results
  • Type-check results
  • Runtime verification results

Blockers and Limitations

For any requirement that cannot be completed, document:

  • The requirement
  • Why it could not be completed
  • Evidence of the blocker
  • What remains to be done
  • Whether the blocker is temporary or permanent

Verification Requirements

After implementation is complete, perform all validation steps described by the documentation.

This includes, where applicable:

  • Dependency installation
  • Build execution
  • Test execution
  • Linting
  • Type checking
  • Database migrations
  • Asset generation
  • Application startup verification
  • Integration verification

If any validation step fails:

Investigate the cause.

Fix the issue.

Re-run validation.

Document the issue and resolution in SETUP_STEPS.md.

Do not consider the task complete while known validation failures remain unresolved unless the documentation explicitly permits them.

Continue-Until-Blocked Rule

Continue working until all documented requirements have been implemented.

Do not stop because:

  • The task appears large.
  • Multiple files must be created.
  • Additional documentation is discovered.
  • Intermediate milestones are reached.
  • The implementation spans many directories or technologies.

If progress is blocked by:

  • Missing credentials
  • Missing secrets
  • Missing API keys
  • Unavailable services
  • Missing infrastructure
  • External system restrictions
  • Permission limitations

Then:

Continue implementing everything else that can be completed.

Clearly document the blocker in SETUP_STEPS.md.

Record exactly what remains blocked.

Record what information or resources are required to continue.

Repository Verification Requirements

Before completion:

Compare the implemented project against all documented requirements.

Verify that each documented requirement maps to:

  • An existing file,
  • An implemented feature,
  • A configuration,
  • A dependency,
  • A test,
  • Or a documented blocker.

Verify that no documented requirement remains unaccounted for.

Completion Requirements

Only stop when the completion checklist below can be satisfied.

Completion Checklist

Before finishing, verify and document that:

  • All documentation referenced from project-setup/index.mdx has been processed.
  • All required files have been created.
  • All required directories have been created.
  • All dependencies have been installed and configured.
  • All configuration requirements have been implemented.
  • All documented features have been implemented.
  • All environment variables have been configured.
  • All required tests have been added or implemented.
  • Builds complete successfully.
  • Tests pass successfully.
  • Linting passes successfully.
  • Type checking passes successfully.
  • The application starts successfully (if applicable).
  • Runtime verification has been completed (if applicable).
  • Each documented requirement has been verified against the repository.
  • No documented requirement remains unimplemented unless documented as blocked.
  • SETUP_STEPS.md contains a complete chronological record of work performed.

Final Verification Report

Before stopping, create a final section in SETUP_STEPS.md named:

Implementation Summary

Include:

  • Total documentation files processed
  • Total files created
  • Total files modified
  • Total directories created
  • Dependencies installed
  • Validation steps executed
  • Validation results
  • Blockers encountered
  • Remaining work (if any)
  • Explicit confirmation of whether all documented requirements were completed

Important Constraints

  • Do not only explain what should be done.
  • Do not replace implementation with a plan.
  • Do not skip implementation steps.
  • Do not omit validation steps.
  • Do not leave documented requirements unfinished.
  • Do not stop after creating scaffolding if the documentation requires implementation.
  • Do not claim completion without verification.
  • Do not assume success; validate it.
  • The completed project is the primary deliverable.
  • The implementation log is supplementary and exists for auditing and verification.

Expected Deliverables

A fully implemented project that follows project-setup/index.mdx and all recursively referenced implementation-related documentation.

A root-level SETUP_STEPS.md file containing a complete chronological implementation and validation log.

A project that successfully passes all documented validation requirements and is runnable according to the documentation.

A final verification report demonstrating that every documented requirement has been implemented, validated, or explicitly documented as blocked.
